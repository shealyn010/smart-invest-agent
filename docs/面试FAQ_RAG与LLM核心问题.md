## 一、RAG中文档切片（Chunking）策略

### Q1: 为什么要做文档切片？不切直接塞给LLM不行吗？

**答**：三点原因——

1. **上下文窗口限制**：LLM的context window有限（如DeepSeek 64K/128K token），长文档直接塞会超出限制
2. **检索精度**：整篇文档粒度太粗，检索时无法精确定位到相关段落；大段文字会稀释关键信息的语义密度
3. **成本与效率**：更长的prompt意味着更高的token消耗和更慢的响应速度

### Q2: 常见的切片策略有哪些？各自优缺点？

| 策略 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **固定长度切片** | 按N个字符/token切，带overlap | 简单、快速 | 可能在句子中间截断，语义不完整 | 通用场景、快速原型 |
| **基于句子** | 按句号/换行等自然断句切 | 语义单元完整 | 不同句子长度差异大 | 对话记录、新闻 |
| **基于段落** | 以Markdown标题、空行分段 | 信息结构完整 | 段落长度不可控 | 技术文档、手册 |
| **递归字符分割** | LangChain RecursiveCharacterTextSplitter | 优先级逐级退化，兼顾语义和长度 | 参数需调优 | **推荐方案** |
| **语义分割** | 用embedding算语义相似度，在相似度骤降处切 | 语义一致性最好 | 计算量大、速度慢 | 高质量知识库 |
| **文档结构感知** | 根据PDF/HTML/MD的标题层级切 | 保留文档原生结构 | 不同格式需适配 | 结构化文档 |

### Q3: 这个项目中的切片策略是怎么选的？

```python
# 采用递归字符分割（RecursiveCharacterTextSplitter）
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # 每个chunk最多500字符
    chunk_overlap=80,    # 相邻chunk重叠80字符
    separators=["\n\n", "\n", "。", "；", ".", " ", ""]  # 优先级递减
)
```

**选择理由**：
- `chunk_overlap=80` 保证关键信息不会因切在分界处而丢失
- 分割符优先级 `\n\n → \n → 。 → ；` 确保优先在自然段落和完整句子处切断
- `chunk_size=500` 针对中文政策文档（信息密集），500字符约含2-3个政策要点，粒度适中

### Q4: 切片大小怎么选？太大了或太小了会怎样？

| 切片大小 | 问题 | 
|----------|------|
| **太小（<100字符）** | 信息碎片化，一个知识点被拆到多个chunk；检索时相关chunk不完整 |
| **太大（>2000字符）** | 检索返回大量无关信息（噪音），LLM注意力分散，关键信息被稀释 |
| **推荐（300-800字符）** | 兼顾信息完整性和检索精度，具体取决于文档类型 |

**实践中**：政策文档偏短（300-500），技术文档偏长（500-1000），对话记录按轮次切。

## 二、如何避免LLM产生幻觉（Hallucination）

### Q5: 什么是LLM幻觉？有哪些类型？

LLM幻觉指模型生成的内容与事实不符。常见三类：

1. **事实性幻觉**：编造不存在的数据、人物、事件（如"某公司成立于2010年，实际是2015年"）
2. **逻辑性幻觉**：推理过程正确但结论错误，或前后矛盾
3. **来源性幻觉**：声称信息来自某个来源，但实际不存在该来源

### Q6: RAG如何减少幻觉？

RAG（Retrieval-Augmented Generation）的核心机制：

```
用户提问 → 向量检索从知识库中找相关文档 → 将文档片段作为上下文注入LLM → LLM基于上下文生成回答
                                   ↑
                            幻觉防护的关键：
                            LLM不是从训练记忆中"回忆", 而是从注入的文档中"阅读理解"
```

**具体做法**：

1. **检索质量保证**：
   - 使用高质量的embedding模型（如本项目使用的BGE-small-zh，中文语义理解优秀）
   - 合理设置检索数量（top_k=5），过少信息不足，过多引入噪声
   - 对检索结果做重排序（rerank），滤除不相关的chunk

2. **Prompt工程约束**：
   ```
   请根据以下知识库内容回答用户问题。
   如果知识库中有相关信息，请依据知识库内容给出详细回答。
   如果知识库中没有直接相关信息，请明确说"根据现有资料，我无法回答这个问题"。
   不要编造任何不在知识库中的具体数据或事实。
   ```

3. **来源标注与可追溯**：
   - 每个回答标注引用了哪些文档，用户可以自行验证
   - 本项目Streamlit UI中展示了"参考来源"

### Q7: 除了RAG，还有哪些减少幻觉的技术？

| 技术 | 原理 | 成本 | 
|------|------|------|
| **Chain-of-Verification** | LLM先生成回答，再自动生成验证问题，逐一核实 | 3-5倍token |
| **Self-Consistency** | 多次采样生成多个候选回答，选一致性最高的 | N倍token |
| **Tool Use/Function Calling** | 不依靠模型记忆，直接调用外部API获取真实数据 | 需维护工具 |
| **Fine-tuning** | 在特定领域数据上微调，降低泛化幻觉 | 需算力和数据 |
| **Constrained Decoding** | 限制模型只能从给定知识库中选词生成 | 灵活性差 |

### Q8: 如何判断一个RAG系统是否"好"？

评估框架（RAGAS标准）：

| 维度 | 指标 | 含义 |
|------|------|------|
| **Faithfulness** | 忠实度 | 回答中的每句话是否都能从检索文档中找到依据 |
| **Answer Relevance** | 回答相关性 | 回答是否直接回应了用户问题 |
| **Context Recall** | 上下文召回 | 检索到的文档是否覆盖了回答所需的所有信息 |
| **Context Precision** | 上下文精度 | 检索到的文档中相关文档的占比 |

## 三、如何保证模型不乱编——边界回答控制

### Q9: "只回答知道的"——这本质是什么问题？

这是**知识边界感知（Knowledge Boundary Awareness）**问题。LLM天生不具备"不知道"的概念——它被训练为"尽最大努力预测下一个token"，而不是"判断自己是否知道答案"。

所以需要从**系统设计层面**人为构建这个边界。

### Q10: 具体怎么实现边界控制？

**方案一：Prompt层面——明确指令**

最直接的做法，在system prompt中明确：

```
你是专业的招商顾问助手。严格遵循以下规则：
1. 只基于提供的知识库内容回答
2. 如果问题超出知识库范围，回复："根据现有资料，我无法回答这个问题。建议咨询相关部门获取更详细的信息。"
3. 不要编造具体数字、日期、人名。如果知识库中没有，不要凭空补充。
4. 如需推测，必须以"根据经验推测……"开头，并明确这是推测而非事实。
```

**方案二：检索层过滤——置信度阈值**

```python
# 检索后检查相似度
results = vector_store.similarity_search_with_score(query, k=5)

# 如果最高相似度仍低于阈值，说明知识库中没有相关信息
if results[0][1] < 0.6:  # 阈值可调
    return "根据现有资料，我无法回答这个问题。"
```

**方案三：两阶段验证**

```
阶段1（检索+生成）：RAG生成初步回答
阶段2（验证）：用另一个LLM调用检查初步回答中的每个事实陈述是否都能在检索文档中找到依据
若某句找不到依据 → 标记为"不确定"或删除
```

**方案四：结构化输出约束**

```python
# 要求LLM以JSON结构化输出，强制区分已知/推测
response_schema = {
    "基于资料的确定信息": "...",
    "基于经验的推测（如有）": "...",
    "无法回答的部分": "...",
    "建议获取更多信息的途径": "..."
}
```

### Q11: 这些方法各有什么权衡？

| 方法 | 可靠性 | 复杂度 | 响应速度 | 用户体验 |
|------|--------|--------|----------|----------|
| Prompt约束 | 中 | 低 | 快 | 可能过于保守 |
| 相似度阈值 | 中 | 低 | 快 | 容易漏掉相关信息 |
| 两阶段验证 | 高 | 高 | 慢 | 好 |
| 结构化输出 | 高 | 中 | 中 | 好 |

### Q12: 实际项目中的推荐组合

```python
# 推荐方案：Prompt约束 + 相似度软过滤 + 前端展示置信度
def safe_query(question: str) -> dict:
    # 1. 检索
    results = vector_store.similarity_search_with_score(question, k=5)

    # 2. 计算置信度
    scores = [score for _, score in results]
    avg_score = sum(scores) / len(scores) if scores else 0

    # 3. 判断
    if avg_score < 0.5:
        return {"answer": "抱歉，现有资料库中未找到相关信息。", "confidence": "low", "sources": []}

    # 4. 生成回答（Prompt中约束）
    context = "\n".join([doc.page_content for doc, _ in results])
    prompt = f"""基于以下知识库内容回答问题。如果无法确定，请明确说明。
知识库：{context}
问题：{question}
请先给出基于资料的确定回答，如有推测请标注。"""

    answer = llm.generate(prompt)

    return {
        "answer": answer,
        "confidence": "high" if avg_score > 0.75 else "medium",
        "sources": [doc.metadata for doc, _ in results]
    }
```

## 四、补充：其他常见面试问题

### Q13: LangChain中Chain和Agent的区别？

| | Chain | Agent |
|------|-------|-------|
| 执行逻辑 | 固定的、预定义的步骤序列 | LLM自主决策下一步做什么 |
| 灵活性 | 低，流程写死 | 高，根据情况调整 |
| 适用场景 | 已知流程（RAG查询） | 需要推理和决策（谈判对话） |

### Q14: Chroma和其他向量数据库（Pinecone/Weaviate/Milvus）怎么选？

| | Chroma | Pinecone | Milvus |
|------|--------|------|------|
| 部署 | 本地嵌入 | 云服务 | 独立部署 |
| 性能 | 中等规模 | 高并发 | 亿级向量 |
| 成本 | 免费 | 付费 | 免费(自建) |
| 适用 | **原型/小项目** | 生产环境 | 大规模生产 |

### Q15: 如何处理RAG系统中的文档更新？

- **增量更新**：仅对新文档做embed并加入向量库（Chroma支持add_documents）
- **全量重建**：文档结构变更时重建整个collection
- **版本管理**：为不同版本的文档建不同collection，支持A/B测试
- **本项目**：启动时自动从data/目录加载最新JSON和MD重新构建索引
